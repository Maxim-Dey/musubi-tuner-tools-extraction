# Команды Spec Kit для выделения Flux2 Dev LoRA

Отправляйте блоки по одному в одну задачу Codex, открытую в корне этого репозитория. Это сообщения для Codex, а не команды PowerShell. Установленная интеграция использует навыки вида `$speckit-specify`.

Последовательность: `specify → clarify → plan → tasks → analyze → implement → converge`. Уточнение можно пропустить, если после specify нет существенных неоднозначностей. Каждый этап заканчивается отдельно.

Конституция уже существует. Переписывать её не требуется: принцип III допускает несовместимые изменения по явному решению пользователя. Удаление поддержки других моделей и видов обучения — такое решение; поведение сохраняемого обучения остаётся защищено конституцией.

## 1. Спецификация

```text
$speckit-specify

Первая фича: сузить существующий репозиторий до обучения LoRA для FLUX.2 Dev.
Удалить всё, что не относится к этому назначению. Скрипты не должны позволять
обучение других моделей или другие виды обучения.

Прочитай действующую .specify/memory/constitution.md. Не изменяй её.
Удаление чужих моделей, режимов и их публичных команд — моё явное решение
о несовместимом изменении в рамках принципа III. Оно не разрешает менять
сохраняемый алгоритм обучения или остальные принципы. Если действительно
потребуется поправка в конституцию, предложи точный текст и дождись согласия.
Документы Spec Kit пиши на английском, общайся со мной на русском.

Зафиксируй требования:
1. Единственная поддерживаемая модель обучения — FLUX.2 Dev, единственный
   вид обучения — LoRA. Поддержка FLUX.2 Klein также подлежит удалению.
   Удаление должно охватывать исполняемый код и точки входа, а не только
   документацию, меню или видимость CLI-параметров.
2. Сохрани полный необходимый цикл: датасет изображений и подписи,
   кэширование VAE-латентов и выходов Mistral 3, обучение LoRA, сохранение
   весов и состояния, возобновление, генерацию примеров во время обучения
   и логирование. Сохрани необходимые общие функции и зависимости.
3. Исходные шаблоны пользователя:
   flux2dev_lora/dataset.toml и flux2dev_lora/train.toml.
   Они задают обязательный сценарий совместимости, но не исчерпывают
   все полезные возможности обучения Flux2 Dev LoRA.
   Сохрани смысл параметров и значения гиперпараметров, включая
   model_version="dev", network_module="networks.lora_flux_2",
   BF16 DiT/текстового энкодера, FP32 VAE, flux2_shift, adamw8bit,
   накопление градиентов, checkpointing, сохранение, sampling и TensorBoard.
   Не добивайся совместимости удалением или игнорированием настроек.
4. Это шаблоны, а не готовые локальные пути к весам и данным. Они должны
   работать после документированной подстановки реальных ресурсов.
   Согласуй пути между поставляемыми примерами: сейчас train.toml ссылается
   на отсутствующие configs/flux2_dev_style/dataset.toml и sample_prompts.txt.
   Предусмотри корректные ссылки и минимальный пример sample_prompts.txt.
   Гиперпараметры ради исправления путей не меняй.
5. Сохрани математику и поведение обучения Flux2 Dev LoRA: loss, noise,
   timesteps, dtype, gradients, optimizer, scheduler, RNG, resume,
   форматы кэшей и сохраняемых LoRA. Не добавляй оптимизации или функции,
   не необходимые для удаления чужой поддержки и совместимости шаблонов.
6. Удали относящиеся исключительно к исключённым возможностям тесты,
   документацию, примеры, ресурсы и зависимости. Обнови общие материалы
   и README по оставшемуся назначению. Сохрани инструменты разработки,
   Spec Kit, конституцию, необходимые лицензии и атрибуцию.
   Не трогай пользовательские данные, веса, результаты и посторонние правки.
7. В сохранившихся точках входа неподдерживаемые модели, виды обучения
   и неизвестные параметры должны давать понятную ошибку до загрузки
   весов, в том числе при передаче через TOML.

Границы самостоятельной генерации, merge/convert и других вспомогательных
утилит оцени относительно цели фичи. Если из запроса нельзя однозначно
определить их судьбу, вынеси конкретные варианты на уточнение до plan.
Не добавляй новые сценарии обучения по собственной инициативе.

Критерии приёмки должны покрывать весь оставшийся цикл и отсутствие
исполняемой поддержки исключённых моделей, включая скрытые ветви
в общих модулях. Совпадение имени файла с другой моделью само по себе
не является доказательством ненужности его содержимого.

Соблюдай локальный этап конституции: без обучения, GPU-запусков,
скачивания весов, сборки пакетов и проверки на сервере.
В этой команде создай спецификацию, не изменяй прикладной код и конфиги.
После завершения остановись.
```

## 2. Уточнение существенных границ

```text
$speckit-clarify

Проверь спецификацию текущей фичи на неоднозначности, которые действительно
меняют состав удаляемого кода или критерии совместимости.

Прежде всего проверь границы самостоятельной генерации Flux2 Dev,
утилит обработки LoRA и дополнительных режимов обучения Flux2 Dev LoRA,
если их судьба ещё не определена. Генерация примеров во время обучения
уже обязательна по train.toml и не требует повторного согласования.

Не спрашивай о том, что можно установить чтением кода, двух шаблонов
и конституции. Не предлагай расширять фичу. Зафиксируй мои ответы
в spec.md на английском. При отсутствии существенных неоднозначностей
сообщи об этом. Не меняй код или конституцию и не переходи к plan.
```

## 3. План удаления с сохранением зависимостей

```text
$speckit-plan

Разработай минимальный план реализации текущей спецификации.
Используй существующую структуру Python-проекта и механизмы обучения.

До составления перечня удалений проследи реальные зависимости всех
сохраняемых точек входа, включая динамические импорты network_module,
регистрацию архитектур, конфиги, кэши, sampling и resume.

Проверь, в частности, обнаруженные связи:
- flux_2_train_network.py импортирует общие функции через hv_train_network;
- training/trainer_base.py использует функции из hv_generate_video;
- flux_2/flux2_utils.py содержит Klein/Qwen и импорт из zimage;
- networks/lora_flux_2.py использует общую реализацию networks/lora.
Перепроверь эти связи по текущему коду; это исходные ориентиры, а не
исчерпывающий список. Нужные функции переиспользуй из существующих общих
модулей или минимально перенеси туда до удаления их прежних владельцев.
Не оставляй реализацию чужой модели ради одной общей функции.

В plan.md перечисли сохраняемые, изменяемые и удаляемые компоненты
с краткой причиной; для смешанных модулей укажи удаляемые ветви.
Обоснуй удаление зависимостей их фактическим использованием,
а не названием или комментарием в pyproject.toml.

Опиши совместимость обоих шаблонов, корректировку примерных путей,
sample_prompts.txt и команды полного рабочего цикла в quickstart.
Не отключай sampling, TensorBoard или другие настройки ради упрощения.
Проверь доступность всех зависимостей этого сценария в описанной установке.

Включи соразмерные локальные проверки: существующие релевантные тесты,
импорты/CLI без загрузки моделей, разбор реальных шаблонов штатным кодом,
отрицательные случаи TOML/CLI для исключённых режимов и проверки
затронутой логики на малых синтетических данных, где это возможно.
Проверь итоговую конфигурацию после применения defaults, TOML и CLI:
одного ограничения argparse choices недостаточно без проверки TOML.

Сначала установи доступный исходный результат релевантных проверок,
чтобы отличать прежние ошибки от регрессий удаления. Не планируй новые
фреймворки, универсальные реестры или переписывание trainer.
Не подменяй локальными проверками проверку обучения на реальной модели.
Учти ограничения локального этапа и остановись после подготовки плана.
```

## 4. Задачи

```text
$speckit-tasks

Составь tasks.md по согласованным spec.md и plan.md. Для каждой задачи
укажи конкретные файлы, зависимость от предшествующих задач и проверяемый
результат. Обеспечь связь требований спецификации с задачами и проверками.

Порядок должен исключать сломанные зависимости: исходные проверки,
отделение нужных общих функций, удаление чужой поддержки и режимов,
проверка итоговой конфигурации, согласование шаблонов и sample_prompts,
очистка зависимостей/тестов/документации, итоговые локальные проверки
и сверка README. Сохраняй структуру задач по пользовательским сценариям.

Новые тесты нужны для существенных рисков и регрессий; не создавай
тесты ради количества или для повторения устройства реализации.
Удаляемые тесты должны относиться исключительно к удалённой поддержке.
Общие проверки обучения и совместимости не ослабляй ради прохождения.
Не добавляй обучение, GPU, скачивание весов, сборку или серверные задачи
в выполняемый локально список. Не начинай реализацию.
```

## 5. Проверка документов перед реализацией

```text
$speckit-analyze

Проверь согласованность spec.md, plan.md, tasks.md и конституции
для текущей фичи. Работай только на чтение.

Особое внимание: полное удаление чужой исполняемой поддержки, сохранение
зависимостей Flux2 Dev LoRA, совместимость обоих исходных шаблонов,
sampling/resume/TensorBoard, ранняя проверка TOML и CLI, отсутствие
необоснованного расширения или сужения scope и выполнимость локальных
проверок. Не считай отсутствие реальных весов дефектом шаблона.

Удаление других моделей и видов обучения явно разрешено пользователем
в спецификации и соответствует исключению принципа III. Это не разрешение
менять конституцию или поведение сохраняемого обучения.

Для подтверждённых проблем укажи требование, доказательство и конкретное
исправление документов. Если они есть, запроси согласие на этот список;
не правь документы сам. Отдели блокирующие проблемы от необязательных
замечаний. Не запускай implement и не требуй исправлений ради стиля.
```

Если анализ обнаружил проблемы, сначала согласуйте конкретный список исправлений документов, внесите их отдельным сообщением и повторите analyze. Требование согласования здесь взято из установленного `.agents/skills/speckit-analyze/SKILL.md`: «user must explicitly approve before any follow-up editing commands would be invoked manually».

## 6. Первичная реализация

```text
$speckit-implement

Выполни задачи первоначальной реализации текущей фичи из tasks.md,
следуя spec.md, plan.md и конституции. Перед началом проверь, что
блокирующие замечания analyze устранены. Эта команда разрешает
реализацию согласованного объёма и предусмотренные им удаления.

Сначала сохрани необходимые общие функции и перенаправь импорты,
затем удаляй чужие точки входа, реализации и ветви. Не ограничивайся
отключением CLI и не оставляй чужую архитектуру под новым названием.
Сохрани поведение обучения и совместимость пользовательских шаблонов.
Не меняй гиперпараметры, математику или форматы ради прохождения тестов.

Выполни предусмотренные доступные локальные проверки и сверь README
с конечным кодом. Отмечай выполненные задачи по фактическому результату.
Недоступные или не выполненные проверки не отмечай как пройденные.
Соблюдай ограничения локального этапа; не запускай реальное обучение,
GPU, скачивание весов, сборку пакетов или серверную проверку.

Если обнаружится необходимая работа вне согласованного объёма,
объясни конкретное расхождение до расширения реализации.
В конце кратко перечисли выполненное, результаты проверок и ограничения.
Не запускай автоматически converge или следующий раунд исправлений.
```

## 7. Проверка соответствия реализации

```text
$speckit-converge

Сверь текущую реализацию с требованиями spec.md, plan.md, tasks.md
и конституцией. Проверяй результат по коду, а не только по отметкам задач.

Проверь отсутствие исполняемой поддержки других моделей и видов обучения,
включая Klein и скрытые ветви общих модулей; целостность оставшихся
импортов и зависимостей; обработку TOML/CLI; совместимость обоих шаблонов;
кэширование, сохранение/resume, sampling, TensorBoard и README.
Не требуй отсутствия любого упоминания чужой модели: история требований,
лицензии и отрицательные тесты могут содержать такие названия.

Добавляй в tasks.md только подтверждённые невыполненные требования
с доказательством и ссылкой на источник. Не добавляй дубликаты уже
открытых задач, стилевые пожелания, гипотезы или новые функции.
Соблюдай append-only: не меняй код, spec.md, plan.md и прежние задачи.
При отсутствии расхождений не меняй tasks.md.

Если нужны исправления, представь конкретный список с ID задач,
причиной и предлагаемым изменением. Запроси моё согласие на этот список
для следующего раунда и остановись. Не запускай implement автоматически.
После первоначальной реализации разрешены максимум два раунда
исправлений, каждый с отдельным согласием, как требует конституция.
После второго раунда только сообщи оставшиеся подтверждённые проблемы;
не открывай третий раунд без новой инструкции пользователя.

При чистом результате сообщи о завершении только локального этапа
при условии выполнения его обязательных проверок и сверки README.
Отсутствие проверки на реальной модели укажи один раз в итогах этапа.
```

## 8. Исправления после converge — только при необходимости

Замените номер раунда и список ID на фактические значения из отчёта. Отправка заполненного блока означает согласие только на перечисленные исправления. Это согласование предусмотрено разделом Development Workflow действующей конституции: «Fixes require explicit user approval of that list».

```text
$speckit-implement

Согласен на предложенные после последнего converge исправления
раунда <1 или 2>: <точный список ID задач>.

Зафиксируй номер раунда и одобренные ID кратко в tasks.md на английском.
Выполни только эти исправления и необходимые проверки. Это согласие
не относится к другим задачам или следующему раунду.
Сохрани исходные требования, шаблоны и поведение обучения.
Дополнительную работу вне списка сначала обоснуй и согласуй.
Не меняй конституцию и не нарушай ограничения локального этапа.
После исправлений повтори затронутые проверки и сверку README.
Сообщи результаты и остановись перед converge.
```

После каждого одобренного раунда повторите команду из шага 7. После второго раунда цикл заканчивается: либо локальный этап завершён, либо явно перечислены оставшиеся расхождения и недоступные обязательные проверки.
