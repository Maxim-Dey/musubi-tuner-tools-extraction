# Feature Specification: Scope the Repository to FLUX.2 Dev LoRA

**Feature Branch**: `main` (existing branch; no branch hook is configured)

**Created**: 2026-09-20

**Status**: Ready for planning — auxiliary-tool scope confirmed by the user

**Input**: Narrow the existing repository to FLUX.2 Dev LoRA training. Remove executable support for other models, including FLUX.2 Klein, and other training methods. Preserve the complete image-and-caption workflow, existing training behavior, and compatibility with the user's `flux2dev_lora/dataset.toml` and `flux2dev_lora/train.toml` templates. Correct example references and provide a minimal sample prompt file without changing hyperparameters. Remove material exclusive to excluded capabilities while protecting development tooling, Spec Kit, the constitution, necessary attribution, and user files. Reject unsupported choices and unknown configuration before loading weights. The user confirmed that generation is limited to sampling during training, standalone merge/export, conversion, and post-hoc EMA operations are removed, and captions are prepared by the user rather than generated by this repository. This invocation creates specification artifacts only and stops before planning or implementation.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Use the Templates for the Complete Training Cycle (Priority: P1)

As a user training a FLUX.2 Dev LoRA, I can replace documented resource placeholders and follow a coherent workflow from captioned images through caching, training, sample generation, logging, saving, and resumption.

**Why this priority**: Removing unrelated support is useful only if the intended workflow remains complete and the user's configuration still means the same thing.

**Independent Test**: Check template configuration and workflow contracts locally with weight-free checks and small fixtures. Real-model execution is a separate operational acceptance step, not a permitted local check.

**Acceptance Scenarios**:

1. **Given** the templates and documented substitutions for real images, captions, model resources, and writable destinations, **When** the user follows the instructions from the repository root, **Then** dataset and prompt references resolve to supplied files, and no active setting must be deleted, ignored, or retuned to make the configuration valid.
2. **Given** images and captions, **When** VAE latents and Mistral 3 outputs are cached, **Then** the results remain usable by Dev LoRA training with the existing cache names, fields, shapes, precision, and interpretation.
3. **Given** the mandatory template settings, **When** training proceeds, **Then** it honors the original LoRA architecture, precision, noise/timestep settings, optimizer, scheduler, accumulation, checkpointing, and data-handling semantics.
4. **Given** the configured saving, sampling, and logging events, **When** those events are due, **Then** LoRA weights, full state, sample images, and TensorBoard records are produced with the original timing, naming, retention, and metric meanings. Step intervals count optimizer updates.
5. **Given** a compatible existing state checkpoint, **When** training resumes, **Then** it restores LoRA, optimizer, scheduler, progress, and RNG according to the existing contract, and subsequent updates and scheduled events match baseline behavior.
6. **Given** a previously supported optional Dev LoRA configuration outside the templates, **When** it is used after narrowing, **Then** it remains supported unless it belongs to an explicitly excluded capability. The templates are a required case, not the complete allowed feature set.

---

### User Story 2 - Have One Supported Training Model and Method (Priority: P1)

As a user or maintainer, I can rely on the repository to train only FLUX.2 Dev LoRA, without executable alternatives hidden behind generic commands or shared modules.

**Why this priority**: Hiding commands or editing documentation alone would leave the narrowing incomplete.

**Independent Test**: Inspect every distributed execution surface and reachable capability, including shared code, and perform suitable weight-free rejection checks.

**Acceptance Scenarios**:

1. **Given** the narrowed repository, **When** root scripts, package/module entry points, registries, factories, dynamic selections, and shared branches are inspected, **Then** no executable support remains for excluded models or training methods, including all Klein variants, full fine-tuning, LoHa, and LoKr.
2. **Given** unsupported model or method selections in CLI arguments, supported TOML inputs, or their combination, **When** a retained entry point validates the effective configuration, **Then** it exits nonzero with an actionable error before loading any weights.
3. **Given** an unknown, misspelled, or removed parameter in a consumed configuration source, including a TOML section, **When** configuration is read, **Then** it is rejected rather than ignored or silently attached to the effective configuration. The diagnostic identifies source, parameter/value, cause, and correction.
4. **Given** common functions stored in or re-exported through files named for another model, **When** unrelated support is removed, **Then** necessary Dev behavior survives and excluded executable behavior does not. A filename alone justifies neither deletion nor retention.

---

### User Story 3 - Preserve Existing Training and Artifacts (Priority: P1)

As a user with existing Dev LoRA runs and artifacts, I retain the original training algorithm and artifact compatibility after the repository is reduced.

**Why this priority**: Successful startup or even a completed run does not prove numerical correctness or reproducibility.

**Independent Test**: Compare retained behavior with the pre-change baseline through source review and suitable deterministic, weight-free regression checks. Record unavailable checks as unperformed.

**Acceptance Scenarios**:

1. **Given** equivalent valid inputs, configuration, and RNG state, **When** training behavior is compared with the baseline, **Then** loss and weighting, noise, timesteps, data processing, dtype transitions, gradients and accumulation, optimizer updates, and scheduler progression remain equivalent under the same existing numerical expectations.
2. **Given** caching, sampling, logging, saving, and resume operations, **When** they are compared with the baseline, **Then** their RNG handling and effects on subsequent training remain unchanged; narrowing adds no training updates or altered objective.
3. **Given** compatible existing Dev caches, LoRA weights, and saved states, **When** they are inspected or consumed, **Then** their formats and interpretation are preserved without migration or regeneration caused by cleanup.

---

### User Story 4 - Use a Focused Repository Without Losing Personal Work (Priority: P2)

As a user or contributor, I find documentation and dependencies for the retained purpose while my data, weights, results, and unrelated edits remain untouched.

**Why this priority**: Cleanup must reduce maintenance burden without damaging user work or removing necessary tools.

**Independent Test**: Review the change inventory, actual dependency use, documentation links, and protected-file baseline without running training or packaging.

**Acceptance Scenarios**:

1. **Given** tests, documentation, examples, assets, and dependencies exclusive to excluded capabilities, **When** cleanup is complete, **Then** those items are removed and shared materials describe the retained scope consistently, including every retained README variant.
2. **Given** necessary common functions, runtime dependencies, development tools, Spec Kit artifacts, licenses, and attribution, **When** narrowing is complete, **Then** they remain available; names and historical dependency comments alone do not establish irrelevance.
3. **Given** user-owned data, weights, caches, results, and unrelated edits, **When** cleanup is performed, **Then** they remain untouched. Later edits to the designated templates are limited to agreed path/documentation corrections and preserve settings and unrelated content.
4. **Given** the narrowed generation scope, **When** executable commands and shared code are reviewed, **Then** no standalone image-generation command or independent inference workflow remains, while sampling during training retains its original behavior.
5. **Given** the removal of independent weight processing, **When** executable commands and their implementations are reviewed, **Then** standalone merge/export, conversion, and post-hoc EMA operations are absent, including `save_merged_model`, while internal operations necessary for retained training, sampling, and saving remain intact.
6. **Given** captions prepared by the user, **When** the dataset workflow is followed, **Then** those captions are consumed as before without an automatic captioning command or a Qwen2.5-VL caption-generation dependency.
7. **Given** the confirmed auxiliary-tool scope below, **When** documentation, tests, examples, assets, and dependencies are reviewed, **Then** items exclusive to removed utilities are absent, and no removed utility has been ported into a new feature.

### Edge Cases

- Klein selections include `klein-4b`, `klein-base-4b`, `klein-9b`, and `klein-base-9b`, including selections appearing only in TOML.
- A valid CLI override does not make an unknown key elsewhere in a consumed source acceptable. Existing precedence for valid defaults, TOML, and CLI inputs remains intact, followed by effective-value validation.
- Alternate network module names, plugin selections, nested network arguments, and legacy aliases must not enable excluded training methods. Necessary common LoRA internals may remain.
- Image training must not keep executable video/audio-specific branches merely because they share dataset, cache, sampling, or trainer code.
- Dataset and prompt-file settings are configuration surfaces too: unknown or excluded options must not be silently accepted before later loading the model.
- Supplied dataset/prompt references must exist in the distribution; external weights and data are documented placeholders, not missing repository deliverables.
- Mistral 3 requires companion shards and tokenizer/processor resources. Instructions must distinguish external prerequisites from supplied files without inventing another weight format.
- Removing standalone generation or merging must not remove internal operations necessary for retained training, caching, sampling, or artifact I/O.
- An absent optional dependency must not silently disable an active setting, substitute an optimizer, or change precision.
- Required generic algorithms can remain despite historical names referring to other models. Excluded model implementations cannot remain merely under new names.
- Untracked files are not disposable cleanup targets; the initial user templates are untracked and must be protected accordingly.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The only supported training model MUST be FLUX.2 Dev, and the only supported training method MUST be LoRA. All Klein variants and every other training model MUST be removed from executable support.
- **FR-002**: Removal MUST cover root commands, package/module entry points, registrations, model loaders and implementations, alternative trainer/network factories, and excluded shared branches. Keeping excluded executable code while hiding its CLI choices or documentation is insufficient.
- **FR-003**: Non-LoRA training, including full-model fine-tuning, LoHa, and LoKr, MUST be removed. The unfinished separate Self-Flow training path MUST NOT be completed or introduced into the retained workflow; support exclusive to that alternate objective is outside the preserved baseline. Useful options of the standard Dev LoRA path MUST NOT be removed merely because the templates do not exercise them.
- **FR-004**: The retained workflow MUST include image datasets and captions, VAE latent caching, Mistral 3 output caching, LoRA training, weight and full-state saving, resume, training samples, and logging. Every required common function and dependency MUST remain available.
- **FR-005**: Both templates MUST remain accepted with every active setting honored after documented resource-path substitutions. Parameter meaning, configured values, and relevant existing defaults MUST remain unchanged except for the required example-path corrections.
- **FR-006**: The mandatory compatibility values below MUST be preserved. Compatibility MUST NOT be achieved by deleting or ignoring settings, retuning hyperparameters, changing precision, disabling samples/logging/saving, or substituting another optimization method.
- **FR-007**: During implementation, `flux2dev_lora/train.toml` MUST reference `./flux2dev_lora/dataset.toml` and `./flux2dev_lora/sample_prompts.txt` instead of the nonexistent `configs/flux2_dev_style/...` files, consistently with repository-root execution. A minimal valid nonempty `sample_prompts.txt` MUST be supplied and usable by the retained training sampler.
- **FR-008**: Documentation MUST explain substitution of model, shard, tokenizer/processor, image/caption, cache, output, and logging resources, relative-path resolution, both caching stages, training, sampling, logging inspection, and resume. Examples MUST NOT imply placeholder resources are present locally.
- **FR-009**: For supported inputs, narrowing MUST preserve loss and weighting, noise generation, timestep selection/shifts, dataset preprocessing/order, dtype behavior, gradients/accumulation, optimizer/scheduler behavior, RNG consumption/restoration, and resume semantics.
- **FR-010**: Existing Dev latent caches, Mistral 3 caches, LoRA weights, metadata, and saved-state formats MUST remain compatible. Save/sample intervals, retention, naming, and logging semantics MUST remain unchanged, including after resume.
- **FR-011**: Retained entry points MUST validate effective configuration after existing defaults, TOML, and CLI precedence and report model-independent errors before weight loading. Unsupported model/method values and unknown or removed parameters MUST fail clearly, including TOML keys. Diagnostics MUST identify source, cause, and correction; ignoring or silent fallback is forbidden.
- **FR-012**: Early validation MUST cover each retained command's consumed configuration sources, including dataset and sample-prompt settings and relevant nested arguments. This does not require adding TOML support to commands without it.
- **FR-013**: Tests, documentation, examples, assets, and dependencies exclusive to excluded capabilities MUST be removed. Shared items MUST be retained or narrowed by actual retained use, not filename matching. Meaningful expectations in retained tests MUST NOT be weakened.
- **FR-014**: README and retained common documentation MUST accurately describe Dev LoRA as the training scope, remove obsolete usage claims/dead links, and explain retained workflows and deliberate command removals. Development tooling, Spec Kit, the constitution, and required licenses/attribution MUST remain.
- **FR-015**: User datasets, weights, caches, outputs, and unrelated edits MUST NOT be deleted or changed by cleanup. Authorized corrections to the designated templates MUST preserve unrelated user content and hyperparameters.
- **FR-016**: No new training scenario, optimization, benchmark, gratuitous dependency upgrade, or general subsystem redesign MUST be introduced. Changes MUST use existing mechanisms and be limited to removal, retained-workflow preservation, strict configuration errors, and template compatibility. No unnecessary weight duplication or tensor retention may be introduced.
- **FR-017**: Verification MUST cover every retained workflow stage and every excluded capability, including shared code and non-public selection paths. Suitable existing checks and focused regression checks for substantial changes MUST be used; unavailable checks MUST NOT count as passed.
- **FR-018**: The local stage MUST NOT run training, GPU work, weight downloads, package builds, server transfer, or server verification. Local contract checks MUST be distinguished from real-model verification; absent external runs MUST be recorded once in the stage's final results.
- **FR-019**: Constitution 1.0.0 MUST remain unchanged. The user's explicit Principle III decision authorizes removal of excluded models, modes, and public commands only, not changes to retained algorithms or other principles. Any actual constitutional conflict requires exact amendment wording and explicit agreement before that change.
- **FR-020**: This specify invocation MUST change only specification/checklist artifacts and Spec Kit active-feature metadata. It MUST NOT modify application code/configurations, example templates, README, or the constitution, and MUST stop before planning/implementation.
- **FR-021**: Generation MUST be limited to sampling during training. Standalone image-generation, merge/export, conversion, post-hoc EMA, and automatic caption-generation commands and their exclusive implementations MUST be removed, including package/module execution paths and corresponding settings such as `save_merged_model`. Users supply prepared captions. Necessary common internals for retained training, caching, sampling, and artifact I/O MUST remain; these removals MUST NOT change standard LoRA saving, resume, or training behavior. Documentation, tests, examples, assets, and dependencies exclusive to these utilities MUST be removed under FR-013 and FR-014.

### Confirmed Auxiliary-Tool Scope

The user resolved Q1–Q3 after reviewing the draft. These decisions close the auxiliary-tool scope and preserve mandatory caching, training, and training samples.

- **Q1 — Keep only sampling during training**: Remove the standalone `flux_2_generate_image.py` command and independent inference workflow, including their package/module entry points and exclusive implementation. Preserve routines required for unchanged sample generation during training.
- **Q2 — Remove standalone weight-processing operations**: Remove standalone merge/export, conversion, and post-hoc EMA, including `save_merged_model`, `merge_lora.py`, `convert_lora.py`, and `lora_post_hoc_ema.py` execution paths and their exclusive implementation. The separate `merge_lora.py` targets HunyuanVideo and is removed without porting it. Preserve only shared operations required by retained training, sampling, and artifact I/O; standard LoRA weight/state saving and resume are not standalone export utilities.
- **Q3 — Use user-prepared captions**: The user creates the captions. Remove `caption_images_by_qwen_vl.py`, its package/module entry points, and automatic-captioning-specific code and dependencies. Preserve ingestion of existing captions and Mistral 3 encoding of those captions and training sample prompts.

The existing GUI targets Qwen-Image and Z-Image-Turbo and is exclusive to excluded capabilities; it is removed rather than expanded into a new Dev GUI. Decisions apply to capabilities and execution paths, not indiscriminate deletion of every shared function in a named file. Internal utilities necessary for retained Dev training, caching, samples, and artifact I/O remain.

### Key Entities *(include if feature involves data)*

- **Image dataset**: User images, captions, optional already-supported Dev conditioning data, and preprocessing/repetition settings.
- **Model resource set**: User-supplied Dev DiT, VAE, Mistral 3 shards, and required tokenizer/processor resources.
- **Effective configuration**: Validated defaults and supported configuration inputs, with provenance for actionable errors.
- **Cached inputs**: Existing-format VAE latents and Mistral 3 outputs associated with dataset items.
- **LoRA artifact**: Saved adapter weights and metadata in the current compatible format.
- **Training state**: Adapter, optimizer, scheduler, progress, and RNG information for existing resume behavior.
- **Training observations**: Sample prompts/images and logging records at configured events.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Exactly one training model and one method remain. Review finds zero executable implementations or selection paths for excluded models/methods, including hidden shared branches, with every distributed execution surface accounted for.
- **SC-002**: Both templates retain 100% of active values and meanings apart from the two required internal path corrections and documented resource substitutions. Zero shipped dataset/prompt references are missing, and at least one valid sample prompt is supplied.
- **SC-003**: All nine workflow capabilities—image/caption input, latent caching, text-output caching, LoRA training, weight saving, state saving, resume, training samples, and logging—have acceptance evidence. Locally, each has suitable local evidence or an explicit unperformed-check status; real-model completion is claimed only after separate authorized operational verification.
- **SC-004**: For every retained entry point and applicable configuration source, all checked unsupported model/method and unknown-parameter cases fail before any weight-loading call, with zero silently accepted unknown settings and errors identifying source, cause, and correction.
- **SC-005**: Baseline comparison identifies zero intentional changes to retained numerical behavior, RNG/resume, or artifact formats. All relevant available regression checks pass; numerical checks unavailable locally remain explicitly unverified.
- **SC-006**: The cleanup inventory contains zero unjustified retained items exclusive to excluded capabilities, zero missing necessary shared dependencies, and zero broken internal usage links in retained documentation. There are zero executable standalone generation, merge/export, conversion, post-hoc EMA, or automatic-captioning workflows; training samples and user-prepared caption ingestion remain covered by SC-003.
- **SC-007**: Cleanup makes zero changes to protected user data, weights, results, unrelated edits, or the constitution. Required development tooling and attribution remain present.

## Assumptions

- The pre-change source baseline is commit `bf478828ffa8b5ef3ebdf225ee72431bdb463159`, plus the two user templates present at specification time. This records behavior to preserve, not an instruction to reset the working tree.
- Users supply real resources and a suitable later runtime. Templates contain placeholders, not evidence that local data or weights exist.
- LoRA means the existing standard Dev adapter-training path. Mistral 3 and VAE remain supporting models; their use does not authorize training them or adding another method.
- Preservation depends on actual Dev LoRA use and explicit exclusions, not only template coverage. This feature invents no new conditioning modes, objectives, export formats, or model support.
- Inspection found Dev imports through `hv_train_network.py`, common cache modules containing Hunyuan-specific behavior, and Klein/Qwen branches in FLUX.2 utilities. These demonstrate the need for dependency-aware review; they prescribe no refactoring design and do not permit retaining excluded implementations.
- The constitution permits the expressly approved removals under Principle III. No amendment is required for this specification. All other principles and subsequent approval gates remain in force.
- This phase ends after specification and clarification. Planning, implementation, and server/real-model verification are separate phases and are not executed by this command.
