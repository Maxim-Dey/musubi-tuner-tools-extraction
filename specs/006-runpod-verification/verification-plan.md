# Predeclared RunPod Verification Protocol

This document fixes the G01–G10 checks **before** any remote model run. Commands below are templates for the later Preparation phase, not claims that they ran. Set `R=/workspace/musubi-val-loss-tests/<run_id>`, `PY=$R/.venv/bin/python`, `SRC=$R/code`, and `CASES=$R/experiments` after the unique run is created. Each opt-in trainer config is `$CASES/<case>/train.toml` with `experiment_dir="."`, canonical train/val dataset TOMLs beside it, and its own `output/`. G05-off is the legacy exception: its isolated config omits `experiment_dir` and `val_dataset_config` and disables samples. Shared frozen fixture images/caches live under `$R/fixtures/`; scenario dataset TOMLs point to those exact absolute paths. G03 renamed/reordered source copies use separately prepared source-bound caches and a separate frozen manifest. `run_case.sh` is a small planned launcher that records command, PID, start/end time, stdout, stderr and exit code in `$R/evidence/<case>/`, then refuses a second launch under the same case ID. A reconnect first inspects that PID and its files.

## Hard gates and fixed settings

Before any optimizer update: verify selected Pod and host key, exact base commit plus transferred source hashes, isolated venv and dependency imports, model headers/paths, fixture image/caption SHA-256s and role relationship, both cache types, frozen Stage 1 fingerprint, free space/VRAM, and the **effective** `max_train_steps`/accumulation/validation/save/sample controls in every TOML. Reject an inherited 1,600-step budget. The observed Pod has one L40S, so G09 is NOT RUN unless a fresh inventory of this same Pod finds two suitable GPUs. A model-format mismatch, OOM at required 1024/BF16/no-FP8/no-block-swap settings, or unreliable source transport is reported with its own environment/transport category; no weakened replacement run is counted.

All real training cases retain Qwen original, LoRA `network_dim=network_alpha=16`, original BF16 DiT, `mixed_precision=bf16`, SDPA, AdamW8bit, `learning_rate=5e-5`, gradient checkpointing, `resolution=[1024,1024]` buckets, FP32 sole adapter state, and FP8/block swap off. Short-case deviations from the Stage 4 example are recorded in each effective TOML: warmup **2 optimizer steps**, exact budgets and intervals below, `val_seed_noise=42`, `N1=4,N2=2`; G09 alone uses `2×1`. One fixed prompt, seed and four inference steps are used where sampling is enabled. Validation-only G03 `10×1` loads the same LoRA weights in a separate experiment; it does not resume or append the `4×2` history. No real-model update is added to chase a loss or image outcome.

### Predeclared comparisons

| Measurement | Criterion on the same observed backend/device | Rationale |
| --- | --- | --- |
| Counts, step labels, image SHA-256 IDs, role membership, `(i,j)` checks, seeds, midpoint `t`, derived timestep, noise tensors and RNG state | Exact equality; compare noise tensor bytes/dtype/shape and state tensors or serialized values. | These are frozen discrete inputs, not estimated model outputs. Reordering compares by `(image ID,i,j)`, not enumeration order. |
| Module modes, existing gradients, LoRA values, optimizer/scheduler state immediately before/after validation | Exact equality, including `None` gradients and all used CUDA generators. | Evaluation must not mutate training state. |
| G03 repeated six metric scalars at unchanged weights | `rtol=1e-3`, `atol=1e-4` per scalar; all finite. | Same L40S/BF16 backend can vary low-order reductions while inputs are exact. No cross-device bitwise claim. |
| G04 independent per-check weighted MSE, image-first set/low/high means and `(low+high)/2` | `rtol=5e-3`, `atol=5e-4` per scalar; all finite. | Reference reduces captured BF16-forward values independently; allowance covers BF16/reduction order, not changed formulas. |
| G05 paired four-update training losses | `rtol=1e-3`, `atol=1e-4` per completed update. | Identical batches/noise should keep losses close despite BF16 kernels. |
| G05 paired LoRA parameter changes | `rtol=5e-3`, `atol=1e-5` tensorwise, plus finite norms. | BF16 forward/backward and 8-bit optimizer can change low-order values. |
| TensorBoard scalar versus its emitted evaluation value | `rtol=1e-5`, `atol=1e-6`; tag/step multiplicity exact. | Event serialization may round a Python scalar to float32. |

The `rtol`/`atol` values above are frozen before results. A failed comparison remains FAIL; never tune tolerance, change fixture, repeat a successful run, or perform extra training to obtain a desired value. Compare checkpoint tensors and loaded optimizer/scheduler/RNG **exactly** before any resumed update. For G04, compute the reference from captured actual `t`, latent, epsilon, model output, target and weighting on selected real forwards; **do not call** the tool's validation aggregation/reducer as the expected-value path. Keep only bounded per-check scalar records and selected tensor evidence, not whole-model dumps.

## Update budget and stopping rules

`G01 12 + G02 10 + G05 4+4 + G06 4+4 = 38` real-model completed updates on one GPU; conditional G09 adds 2 for a hard maximum of **40**. G03/G04/G07/G08/G10 add none. A skipped optimizer attempt does not consume the completed-update budget, but a case must never silently extend beyond its declared target; record attempts and completed counts. Before each training launch, parse the **effective** TOML and CLI values and compare them with the row above; refuse a 1,600-step fallback. After a disconnect, inspect recorded PID, status, logs and output before any retry. A successful case is never rerun without a code change or concrete unresolved question. Functional failure is reported, not repaired on the Pod; product fixes follow the constitution's separate discrepancy approval process. The user alone manages Pod lifecycle.
