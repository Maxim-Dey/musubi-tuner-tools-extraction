# Команды Codex для детерминированного val-loss

Одна фича, одна спецификация и пять отдельных этапов реализации. Команды ниже предназначены для Codex с установленными в репозитории навыками Spec Kit. Конфиги, код и проверки создаёт агент при выполнении серии.

Для автономного выполнения отправьте Codex весь этот документ с указанием выполнить команды 0–12 по порядку. При поэтапной подаче копируйте содержимое соответствующего блока целиком. Команды вводятся в чат Codex, а не в терминал. Синтаксис `$имя-навыка` соответствует установленной интеграции и [документации Codex](https://developers.openai.com/plugins/build/skills).

Конституция версии 2.0.0 уже закрепляет автономное выполнение, проверку и до двух раундов исправления подтверждённых дефектов без ручного одобрения. Команда 0 запускает работу по этим правилам; менять конституцию или повторно запускать `$speckit-constitution` в этой серии не требуется. Локальные проверки и удалённые GPU-проверки остаются разными этапами, переход между ними выполняет агент. Лимит раундов общий для фичи; при оставшихся после него дефектах агент сообщает о незавершённости.

Принятые при формализации решения: три метрики считаются только на `val`; `train` используется для обучения и проверки отсутствия пересечения. Новый режим эксперимента включается явно, чтобы сохранить старые конфиги. При resume `max_train_steps` означает целевой суммарный шаг в новом режиме. Эти решения полностью включены в команды.

## Команда 1 Спецификация

```text
$speckit-specify

Создай одну новую фичу «Deterministic validation loss and noise-level breakdown» для сохранённого Qwen-Image original LoRA trainer.
SPECIFY_FEATURE_DIRECTORY=specs/002-deterministic-val-loss
Если нужна новая ветка: codex/deterministic-val-loss.
Сохрани корректный feature_directory в .specify/feature.json. Документы прежней фичи не переписывай. Если эта спецификация уже создана предыдущим выполнением серии, продолжи её, не создавая дубликат.

Работай автономно с субагентами по правилам команды 0. Координатор записывает спецификацию; независимый агент проверяет полноту. Ниже приведён полный контракт фичи. Формулы, имена параметров, метрик и ограничения сохраняй как обязательные требования. Не подменяй их общими формулировками о воспроизводимости.

1. Область и включение
- Существующее обучение Qwen-Image original и его loss сохраняются. Фича добавляет измерение val-loss, корректную шкалу шагов при resume и структуру одного эксперимента.
- Наличие val_dataset_config включает валидацию; без него её нет. Неизвестные параметры и явно заданные параметры val без val_dataset_config — ранняя понятная ошибка.
- Для новой организации путей и сохранений введи experiment_mode=true, по умолчанию false. Если оба новых режима выключены, старые команды, конфиги, пути и сохранения работают по-прежнему.
- Пользователь заранее готовит непустые train и val. Val содержит изображения, не участвующие в обучении; автоматического разбиения train на val нет. Проверяй непустоту эффективных наборов и отсутствие совпадений train/val по SHA-256 содержимого изображений. Отдельный train-val набор и дополнительные train-val графики не нужны.

2. Неизменность входов
- Val использует фиксированные изображения, подписи, latents, текстовые embeddings и детерминированную подготовку данных. Во время обучения не менять состав, подписи, crop, геометрию или кэши валидации автоматически.
- Batch size и num_repeats для val равны 1. Каждый элемент учитывается один раз до перебора шумов. Несоответствующие настройки отклонять, а не незаметно исправлять.
- Фиксированная подготовка к разрешению и bucket допустима; случайные аугментации, caption dropout, shuffle captions и повторное случайное кодирование val недопустимы.
- Идентификатор изображения — SHA-256 байтов исходного файла, а не путь, индекс загрузки или Python hash(). Переименование, перенос эксперимента и иной порядок загрузки не меняют его шумы.
- Сохраняй достаточный отпечаток входов и параметров валидации для проверки при resume. Изменение val или его кэшей не должно незаметно продолжать прежнюю серию измерений. Пропавшие или некорректные кэши — ошибка, а не пропуск изображения и не пересоздание во время обучения.

3. Уровни и реализации шума
- val_every_n_steps: целое >= 1.
- val_seed_noise: целое; bool не считается целым параметром.
- val_level_noise_n = N1: чётное целое >= 2.
- val_seed_noise_n = N2: целое >= 1.
- Для каждого изображения val выполнить ровно N1*N2 проверок.
- Для i=1..N1: t_i = 0.05 + (i - 0.5)*0.90/N1.
- Low noise: 0.05 <= t < 0.5. High noise: 0.5 <= t <= 0.95. В каждой группе N1/2 уровней.
- t — окончательный коэффициент смешивания: x_t = (1-t)*latent + t*noise. На интерфейсе тренера со шкалой 0–1000 передавать ровно 1000*t. Не применять shift, train timestep sampling, округление к сетке scheduler или добавление 1.
- Для j=1..N2 seed = stable_hash(val_seed_noise, image_sha256, i, j), с SHA-256 и однозначной сериализацией. Конкретный байтовый контракт и преобразование в допустимый seed зафиксировать в plan и тестах. Seed не зависит от шага обучения, epoch, rank, числа workers, пути или порядка загрузки.
- У генерации val-noise отдельный RNG. Изоляция охватывает также загрузчик, подготовку val и любые случайности внутри evaluation. Состояния Python, NumPy, torch CPU и используемых CUDA RNG обучения не меняются.

4. Loss и усреднение
- Использовать те же преобразования latents, forward, target и формулу loss, что в обучении, включая применимые weighting и reduction. Не вводить самостоятельную похожую формулу loss. Для weighting использовать фактический фиксированный t; нельзя незаметно брать другой sigma из сдвинутой сетки scheduler.
- Пусть L[k,i,j] — scalar loss одной проверки после принятого в обучении усреднения элементов изображения; M — число изображений val.
- loss_mean = (1/M)*sum_k ((1/(N1*N2))*sum_i sum_j L[k,i,j]).
- loss_low_noise и loss_high_noise аналогичны, с соответствующими N1/2 уровнями и делителем (N1/2)*N2.
- Изображения имеют равный вес независимо от разрешения, bucket и количества пикселей. Не усреднять средние buckets или ranks без учёта числа изображений. Для нескольких записей datasets все изображения val образуют один общий набор.
- Следствие для тестов: loss_mean = (loss_low_noise + loss_high_noise)/2 с допустимой погрешностью вычислений.

5. Момент и режим выполнения
- Новый запуск: валидация на шаге 0 до первого обновления весов.
- Далее — после каждых val_every_n_steps завершённых обновлений оптимизатора, после gradient accumulation и до следующего train batch. Микробатчи и пропущенные из-за overflow обновления не считать отдельными optimizer steps.
- После последнего завершённого шага выполнить валидацию, если на этом шаге её ещё не было. Совпадение финального и периодического события не создаёт повторной проверки.
- Evaluation без autograd, backward и обновления optimizer/scheduler. Отключить dropout модели и адаптера; исходные training/eval режимы, RNG и временные настройки восстанавливать даже при исключении.
- Валидация не меняет параметры, градиенты, optimizer state, scheduler state, тренировочные batch/timestep/noise последовательности и последующее обновление весов.
- Использовать уже загруженную модель и адаптер. Не дублировать DiT и не хранить все N1*N2 шумов или графы вычислений.
- При нескольких процессах каждая пара image/level/realization учитывается ровно один раз, метрики записывает один процесс. Стратегию синхронизации выбери в plan без зависаний и без повторного учёта sampler padding.

6. TensorBoard и resume
- Добавить ровно три scalar tags: val_loss_mean, val_loss_low_noise, val_loss_high_noise. Существующие train-loss значения и названия сохранить.
- Ось шага для train-loss и val-loss — число завершённых optimizer updates. В новом режиме устранить сброс этого счётчика при resume.
- Сохранять и восстанавливать optimizer_global_step явно: не считать Accelerator.step или номер файла надёжной заменой.
- При resume с шага S продолжить шкалу от S. Перед новым обновлением измерить val на S, если для загруженных весов и тех же входов нет уже сохранённого результата этого шага; одинаковую точку повторно не добавлять. Первая новая train-loss точка относится к реальному продолжению обучения; синтетический train-loss для S не создавать.
- Следующие periodic события определяются абсолютным шагом: S + (val_every_n_steps - S % val_every_n_steps). При совпадении S с периодом следующее событие — S + val_every_n_steps.
- При включённом val или experiment_mode max_train_steps — целевой суммарный optimizer step. Если S уже достиг цели, дополнительные обновления не выполнять.
- Продолжать тот же TensorBoard run при resume; учитывать события после восстановленного checkpoint так, чтобы не показывать прежнюю отброшенную ветку как продолжение. Сохранять достаточно metadata для run, step и deduplication.
- Восстанавливать LoRA, optimizer, scheduler и RNG. Для старого state без новых metadata сохранить legacy-путь загрузки; при запросе нового режима с неизвестным шагом выдать объяснение, а не начать график с нуля.
- Точное восстановление позиции train dataloader сверх существующих возможностей не входит в задачу. Не заявлять bitwise-identical training resume без его проверки. Изоляцию val проверять при одинаковом начальном состоянии и одинаковых train batches.

7. Папка эксперимента и сохранения
- Пользователь выбирает имя папки и помещает туда train.toml, train-dataset.toml, val-dataset.toml, sample_prompts.txt, dataset/train и dataset/val.
- В experiment_mode корень эксперимента — папка основного train.toml. Его относительные пути, включая resume, считать от неё; пути внутри dataset TOML — от папки соответствующего TOML. Абсолютные пути сохранять. Кэш-команды должны поддерживать ту же явную семантику; запуск из другой рабочей папки не меняет выбранные файлы.
- Кэши разделены: cache/train и cache/val. Вывод: output/tensorboard и output/<output_name>-step<optimizer_step>/.
- В каталоге шага находятся samples/, одна каноническая копия LoRA model.safetensors, необходимые файлы optimizer/scheduler/RNG и metadata тренера. Фактические имена вспомогательных файлов брать из поддерживаемого Accelerate, а не воспроизводить декоративную схему.
- model.safetensors должен быть пригоден и для использования адаптера, и для точного восстановления его обучаемых весов через согласованный load hook. При state-сохранении единственная копия адаптера — FP32; конфигурация с потерей точности должна отклоняться заранее. Базовые веса модели не сохранять.
- Не создавать рядом вторую экспортную копию адаптера и отдельную дублирующую копию тех же LoRA tensors внутри state. Финальное и периодическое сохранение одного шага должны давать один checkpoint.
- Samples связывать с фактическим шагом их генерации; несовпадающие интервалы samples/save не должны подменять эту связь. Каталог только с samples не считать resumable checkpoint.
- save_last_n_steps и save_last_n_steps_state — окна в optimizer steps, не число файлов. При меньшем окне state удалять старые optimizer/scheduler/RNG, сохраняя LoRA до истечения окна весов. Пока state нужен, необходимые для resume веса удалять нельзя, даже если окно state больше окна весов. Отсутствующее/нулевое окно state наследует окно весов, как в существующем инструменте; отсутствующее окно весов означает отсутствие ограничения.
- Очистка ограничена артефактами выбранного output_name в этом эксперименте. Проверять завершённость сохранения перед признанием checkpoint пригодным к resume. Сохранять необходимые RNG состояния всех rank.

8. Поставляемый результат
```
